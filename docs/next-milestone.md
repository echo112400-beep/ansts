# 下一里程碑：可控的真实沙箱执行

审视日期：2026-11-14。原提案基线：`b2c259d`。下文保留最初范围与验收门槛；当前实施、部署和验证状态见 [剩余任务交付记录](remaining-work-delivery.md)，不再按本节原始缺口判断现状。

## A 结论与设计目标

下一里程碑让授权任务在受限沙箱中执行指定命令。任务返回可查询的退出码、日志和产物。执行支持取消、资源限额和中断后的保守恢复。

沿用 Gateway → Scheduler → Body celld → 原生 Daemon 的职责划分。Body celld 持有执行准入和状态；Daemon 负责沙箱生命周期和执行事实。不要将容器管理移入 Worker，也不要让 Gateway 承担执行器职责。

完成标准是从“能安全协调一次 trace 写入”推进到“能交付一个有隔离、有资源扣账、有退出证据的真实执行任务”。本轮先支持受信任开发任务，不宣称可承载敌对多租户负载。

## C 分批交付与依赖

| 批次 | 交付内容 | 依赖 | 可演示结果 |
| --- | --- | --- | --- |
| M1.1 执行与容量契约 | 定义 execution spec、结果 schema、资源预留、并发槽与状态转换；默认单槽，容量来自显式配置并受运行环境上限约束 | 无 | 并发提交超过槽位的任务时排队，实际运行不超额；重启后按现存执行事实恢复扣账。 |
| M1.2 受限命令沙箱 | 引入 SandboxRuntime 接口及首个容器 adapter；固定镜像摘要、argv、工作目录、超时与资源限额；默认禁止外网、无服务密钥、无宿主目录挂载 | M1.1 | 两个任务执行不同命令，分别返回退出码、受限日志与工作区产物；互相不可见。 |
| M1.3 生命周期与恢复 | 用户侧状态、取消、Daemon drain；明确准入/预留/启动/退出/提交阶段；统一续租职责；持久结果与回收证据 | M1.1、M1.2 | 排队取消不启动；运行取消确认退出后释放资源；非零退出可查询；无法证明退出时保持阻塞。 |
| M1.4 运维与验收 | 提供任务日志/产物查询、容量与沙箱状态、最小指标和故障测试入口，更新部署与恢复手册 | M1.1–M1.3 | 一条验收命令覆盖正常执行、超时、取消、断网、进程崩溃、恢复和租户隔离。 |

每批独立提交且保持现有 trace 任务兼容。先合并契约和容量，再开放命令执行。首个容器 adapter 不扩展为任意驱动插件体系；后续确有第二种隔离实现时再扩展接口。

## D 必须通过的验收门槛

- **真实执行**：授权租户提交结构化命令，查询退出码、日志和产物；prompt 保持为数据，不能隐式转换成 shell 命令。
- **权限与隔离**：另一租户无法读取任务或日志；沙箱读不到 Body token、存储凭据或宿主目录；默认无法连接控制模块及外网。
- **容量守恒**：并发不超过声明槽位；预留、运行、取消和退出分别验证释放行为；不因断网、drain 或重启重复释放或超卖。资源使用值与配置限额分开呈现。
- **确定失败**：非零退出、超时、已确认取消都有明确结果；只有缺少执行/退出证据才进入 UNCERTAIN。状态转换需先补齐协议，不能把旧 COMPLETED 语义直接复用为执行成功。
- **停止与恢复**：取消前等待沙箱及后代退出；杀死 Daemon 后能发现和回收残留沙箱。启动后无法确认的工作不得自动重跑。drain 停止领取新租约，允许已有任务完成或按策略终止。
- **结果交付**：故障点覆盖退出、日志落盘和结果入 outbox 的间隙。另在 Body finish 后、Scheduler complete 后注入故障。验证相同结果可重试、不覆盖完成事实、最终状态一致。
- **持续性**：至少一个 10 分钟任务经过短暂断网；连续三轮故障矩阵通过，无遗留沙箱或无法解释的资源预留。此项是验收目标，尚未验证。

## E 本轮不纳入与后续顺序

不纳入完整 LLM Agent 工具循环、MicroVM、GPU、warm pool 优化、跨地域迁移和自动恢复未知外部副作用。容器引擎访问由 Daemon 独占，沙箱不可获取引擎 socket；其宿主权限风险必须在部署手册中明确。

M2 处理控制模块可用性：Body 持久状态部署方案、Gateway 状态恢复/共享语义、Scheduler 入口容错，以及数据迁移与回滚演练。先验证存储一致性，再增加入口或副本，不通过多份独立存储制造表面冗余。

生产身份接入可在取得 IdP 配置后独立推进；生产发布前必须补齐 OIDC、服务凭据轮换、具名管理员审计及部署 secret 管理。它们不因开发沙箱完成而自动满足。

## F 实施起点

第一批从 `scripts/body_cell_agent.mjs`、`src/runtime/body_daemon_server.ts`、`src/node_daemon.ts` 与 Scheduler 准入路径入手，完成容量、预留和结果协议。随后将 `runBodyExecution` 后的运行机制替换为受限容器 adapter，复用已有准入、日志和 outbox。

本规划建议优先级为：容量和执行协议 → 真实沙箱 → 生命周期及恢复 → 自动验收 → 控制模块 HA。估时应在 M1.1 的接口和容器运行条件确定后给出，当前不承诺日期。
