## 第一阶段：安全恢复与执行边界

第一阶段是下一轮开发范围。先完成 N1/N2 的协议，再让 N3 使用该协议；N4 以完成后的协议为验收对象。

### N1 / P0：执行尝试状态机与核对工作流

- 修改入口：`body_cell.ts`、`body_cell_agent.mjs`、`body_execution_journal.ts`、Scheduler 状态映射。
- 定义 attemptId、租户、任务、宿主机、fence、输入摘要、结果摘要和单调版本；区分准入、执行中、结果待回报、已完成、结果不确定。
- finish 采用版本/所有权条件更新，完成记录不可被后续不同结果覆盖。重复请求只能返回同一结果。
- 引入查询与核对 API：有证据确认完成、确认未开始后创建新尝试、保留阻塞。不得直接删除准入后盲目重跑。
- 核对写入绑定目标版本、证据、操作者与原因，记录审计。把“不确定”作为可观测状态，避免仅打印错误后无限续租。
- 验收：在准入后、执行前、执行后回执前、回执后完成前分别杀进程；恢复后的任务具有明确状态，无盲目重放；陈旧核对请求返回冲突。

### N2 / P0：身份、租户隔离与执行凭证

- 为 Body 注册、心跳、准入、finish 和核对路由引入身份校验；仅允许受权 host 更新自身状态。
- 统一 `(tenantId, taskId, attemptId)` 标识；检查 Scheduler、Body 寻址、Gateway、日志与结果读取的命名空间，避免跨租户同名任务碰撞。
- 执行凭证绑定 host、attempt、fence、输入摘要和有效期；本地入口同时校验 Scheduler 租约与共享准入。当前本地入口只验证租约，不能据此证明已获共享准入。
- 限制路由方法、字段与请求大小；拒绝未知 Body 写路由，避免当前非 heartbeat POST 默认写 receipt 的行为。
- 凭据由部署 secret 注入，日志脱敏；权限校验完成后再对外提供核对写 API。
- 验收：伪造 host、跨租户同名任务、过期/篡改/重放凭证、绕过代理直调执行、非 owner finish 均被拒绝。

### N3 / P0：可终止执行与可靠结果回传

- 原生工作移到可管理的子进程/执行句柄，定义启动、查询、终止和回收接口。
- 执行期间独立刷新心跳与续租；失租、取消或超时停止整个进程组，并等待退出确认。停止失败进入不确定态。
- 结果读取、落盘与确认期间维持正确的租约语义；当前计时器在 HTTP 返回响应头后清理，需要覆盖完整执行生命周期。
- 持久结果队列重试 finish/receipt/complete；指数退避、抖动及单任务隔离，避免失败任务阻塞健康任务。
- 修正容量上报与 Scheduler 资源扣账契约，验证在途任务不会被重复计费或错误释放。
- 验收：长任务超过原有请求时间仍保持租约；取消/失租后不再产生新副作用；断网回传恢复后只确认一次；重启后无孤儿进程。

### N4 / P0：容器故障矩阵与可观测验收

- 自动化覆盖 Body 重启、租约到期、旧 fence 回报、任务迁移、结果回传断网、重复提交及核对冲突。
- 记录租约续签失败、执行结果不确定、结果队列积压、任务阶段耗时、实际活跃进程数和最后成功心跳。
- 验收：每个场景保留可复现脚本、状态断言及日志；第一阶段全部通过后才称“安全执行闭环完成”。不以单元测试替代容器故障验证。

## 交付顺序与范围

建议下一轮先交付 N1 的数据契约与状态迁移、N2 的身份/标识基础，再交付核对写接口和 N3 执行器，最后运行 N4 故障验收。每项以独立可回滚变更提交；新状态采用兼容迁移，旧记录缺少证据时保守映射为待核对，禁止直接认定可重试。

本计划不预估工期；执行器后端、身份方案和历史记录迁移范围确定后，再按可验收变更拆分估算。
